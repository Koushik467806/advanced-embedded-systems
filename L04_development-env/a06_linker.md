# The Linker in C

The linker is the final stage in the build pipeline. It takes one or more object files (`.o`, `.obj`) and library files (`.a`, `.lib`, `.so`, `.dll`) generated by the assembler/compiler, combines them, and generates the final executable (such as `.exe`, `.elf`, `.hex`, or `.bin`).

---

## Core Tasks of the Linker

| Task | What the Linker does |
| :--- | :--- |
| **Symbol Resolution** | Matches calls to definitions; fails if a definition is missing. |
| **Relocation** | Assigns final memory addresses to code and data. |
| **Library Inclusion** | Extracts needed machine code from libraries (like `-lm`). |
| **Executable Creation** | Formats everything into a final binary (e.g., `.exe` or `a.out`). |

---

## 1. Symbol Resolution
When you write C code, you reference functions and variables declared in other source files. During compilation, the compiler compiles each `.c` file individually into an object file (`.o`).
* The compiler does not know where external functions/variables are located in memory. It leaves placeholders (unresolved symbols) in the object file's symbol table.
* The linker reads all object files, matches every reference to a symbol (e.g., a function call or global variable usage) with its unique definition, and fills in the placeholder.

### Common Symbol Resolution Issues:
* **Undefined Reference (`undefined reference to 'foo'`)**: Occurs when a symbol is declared (e.g., in a header file) and used, but its definition (e.g., in a `.c` file or library) is missing or was not passed to the linker.
* **Multiple Definition (`multiple definition of 'bar'`)**: Occurs when the same global variable or function name is defined in multiple object files. This violates the **One Definition Rule (ODR)**.
  > [!TIP]
  > To avoid multiple definition errors, only *declare* global variables in header files using the `extern` keyword (e.g., `extern int my_var;`), and *define* them in exactly one source file (e.g., `int my_var = 0;`).

---

## 2. Relocation
Each object file is generated as if it starts at address `0`. The compiler doesn't know where the program will finally reside in memory.
* **Section Merging**: The linker merges similar sections from different object files (e.g., all `.text` sections containing code are merged into one large code block; all `.data` sections are merged into one data block).
* **Address Assignment**: The linker assigns absolute memory addresses to these merged sections and updates all internal references (pointers, jump instructions, function calls) to point to these newly assigned addresses.

---

## 3. Linker Scripts (Crucial for Embedded Systems)
In standard desktop programming, the operating system's loader automatically decides where to load the executable. In embedded systems, there is no OS loader; code must run directly from specific physical memory addresses (Flash, RAM, etc.).
* **Linker Scripts (`.ld` files)**: Control how the linker lays out the program in the microcontroller's memory map.
* They define:
  1. **Memory Regions**: The start address and size of Flash (ROM) and SRAM.
  2. **Section Placement**: Which output sections go into which memory regions.

### Common Memory Sections:
* **`.text`**: Read-only section containing the compiled machine code. Placed in **Flash**.
* **`.rodata`**: Read-only data (like string literals, `const` variables). Placed in **Flash**.
* **`.data`**: Initialized global and static variables. Copied from **Flash** to **SRAM** at startup.
* **`.bss`**: Uninitialized global and static variables. Must be cleared to zero in **SRAM** at startup.

---

## 4. Static vs. Dynamic Linking

| Feature | Static Linking | Dynamic Linking |
| :--- | :--- | :--- |
| **Inclusion Time** | Done at build time. | Done at runtime (by the OS loader). |
| **File Size** | Larger executable (contains library code). | Smaller executable (references external files). |
| **Dependencies** | Self-contained; runs without external files. | Requires shared library files (`.so`, `.dll`) on the host system. |
| **Embedded Use** | Standard (embedded systems rely almost exclusively on static linking). | Rare (only used in complex embedded Linux systems). |

---

## 5. Linker Optimization Tips
* **Unused Code/Data Elimination**: By default, the linker includes entire object files even if only one function is used.
  * Use GCC flags `-ffunction-sections` and `-fdata-sections` during compilation to place each function and variable in its own individual section.
  * Use the linker flag `-Wl,--gc-sections` to instruct the linker to perform garbage collection and discard sections that are never referenced.
* **Stripping**: Removing the symbol table and debug information from the final executable to reduce its size for production deployment (using the `strip` command or `-s` flag).
